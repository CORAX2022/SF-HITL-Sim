## 2. ⚠️ 关键发现：`oTree-org/oTree` 不是框架本体

**这是一个会影响集成方案的重要事实，必须澄清。**

`oTree-org/oTree` 仓库内**没有** `pyproject.toml` / `setup.py`，
其顶层内容是 15 个**示例实验应用**：

```
_rooms  _static  _templates
bargaining  bertrand  common_value_auction  cournot  dictator
guess_two_thirds  matching_pennies  payment_info  prisoner
public_goods_simple  survey  traveler_dilemma
```

实测：`Test-Path deploy/repos/oTree/pyproject.toml` → **NO pyproject.toml**

**含义**：
- 该仓库是 **oTree 的官方示例应用库**（教学与范式模板），**不是** oTree 框架源码；
- oTree **框架本体**通过 PyPI 分发（包名 `otree`）；
- 因此"部署 oTree"的正确做法是 `pip install otree`，而该仓库的价值在于
  **15 个可直接借鉴的实验范式模板**（多人博弈、公共品、问卷、支付）。

## 5. 与"真人被试接入闭环实验"的契合点

### 5.1 oTree 提供闭环所需的**同步多轮会话骨架**

| 闭环需求 | oTree 对应能力 | 证据 |
|---|---|---|
| 多名被试同时在线 | `create_session` / 房间机制 | CLI 实测存在 |
| 多轮推进且轮间同步 | `guess_two_thirds` 多轮跑通 | §3.3 原始输出 |
| 每轮采集客观选择 | 表单提交 → 数据库 | `{'guess': 10}` 实测落库 |
| 采集主观量表 | `survey` 应用跑通 | §3.3 原始输出 |
| 数据导出分析 | `--export` → CSV | §3.4 实测文件 |
| 被试支付 | `payment_info` 应用 | 仓库示例 |

**关键**：oTree 的"轮次（round）+ 等待页（WaitPage）"机制与
本项目的闭环时序
（[`docs/model/存量-流量模型规范.md`](../model/存量-流量模型规范.md) §5）
**结构同构**——`WaitPage` 正是"决策窗口关闭后再统一推进"的现成实现。

### 5.2 jsPsych 提供**被试端空间选择界面**的计时与呈现能力

| 闭环需求 | jsPsych 对应能力 |
|---|---|
| 呈现空间状态图 | 自定义 HTML 插件（`index.browser.js` 可嵌入） |
| 精确决策反应时 | 核心计时机制（浏览器实验的标准能力） |
| 选择偏好排序 / 支付意愿 | 成熟问卷与量表插件 |
| 与后端轮次同步 | 通过 `extension` 机制接 WebSocket |

### 5.3 建议的集成方案

```
被试浏览器
   ├─ jsPsych（空间选择界面 + 反应时 + 量表）
   └─ 通过 WebSocket 提交统一决策协议消息
                │
       oTree 会话/轮次骨架（or 自研 WebSocket 房间）
                │
       本项目 src/core 存量-流量内核（已验证 24/24 测试通过）
```

**取舍建议**：
- 若重视**多人同步轮次与支付/问卷**，以 oTree 为会话骨架，jsPsych 嵌为页面；
- 若重视**低延迟状态回传与实时可视化**（每轮都要回传空间状态图），
  自研 WebSocket + jsPsych 更轻；oTree 的整页刷新式轮次在实时性上偏重。
- 两条路都不需要改内核——统一决策协议（架构文档 §3）已把接入点隔离。
