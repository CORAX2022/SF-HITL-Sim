# 用 git 写论文：完整工作流

> 面向课题组青年成员的实操手册。目标不是"学会 git 全部命令"，而是让**每一段正文、
> 每一个数字、每一张图**都能被追溯到"谁、在哪个提交、基于哪份数据改的"。
>
> 适用仓库：本课题组论文仓库（`paper/` 存放论文，`docs/` 存放素材与规范）。
> 所有命令均在 **PowerShell** 中给出，默认工作目录为仓库根目录。

---

## 0. 心智模型：写论文的三条 git 原则

1. **一次提交 = 一个可以一句话说清的变化**。说不清，就说明该拆。
2. **分支管"正在写什么"，标签管"曾经发布过什么"**。不要在 main 上边写边改历史。
3. **数字必须与数据同版本**。改了数据没改正文，等于制造一处无法复现的结论。

## 1. 一次性配置

```powershell
# 身份（提交记录里会永久显示，别用昵称）
git config --global user.name  "你的真实姓名"
git config --global user.email "你的邮箱"

# 换行：仓库统一 LF。Windows 上必须设置，否则每行都会显示为"整段被改"
git config --global core.autocrlf input

# 中文文件名不被转义成 \344\275\240 这类八进制串
git config --global core.quotepath false

# 默认分支名（若本机 git < 2.28，可省略）
git config --global init.defaultBranch main

# 提交信息用编辑器写长说明时的编辑器（可选）
git config --global core.editor "notepad"
```

验证：

```powershell
git config --global --list
```

> **换行约定**：本仓库所有文本文件使用 **UTF-8（无 BOM）+ LF**。
> 若你在 Windows 上保存出 CRLF，导出的 Markdown 会出现多余空行，diff 也会失真。

## 2. 分支模型

### 2.1 三类分支

| 分支 | 作用 | 谁能动 | 生命周期 |
| --- | --- | --- | --- |
| `main` | 稳定线：任何时刻都能导出可读稿 | Lead 合并；其他人不直接推送 | 长期 |
| `writing/<主题>` | 写作线：一章或一个专题的持续修改 | 该章负责人 | 章节合并进 main 后删除 |
| `review/<日期>` | 评审快照：某一时点的全文冻结版，只读 | Lead 创建 | 评审结束后保留或删除 |

命名规则：

- `writing/` 后接**短横线小写英文**或拼音，不用中文与空格：
  `writing/ch02-lit-review`、`writing/ch06-results`、`writing/terminology`；
- `review/` 后接日期 `YYYYMMDD`：`review/20261120`。

### 2.2 分支生命周期

```powershell
# ① 从最新 main 开写作分支
git switch main
git pull --ff-only
git switch -c writing/ch02-lit-review

# ② 写作期间小步提交（见 §4）
git add paper/sections/02-文献综述与研究缺口.md
git commit -m "docs(ch02): 补写 2.3 节 B 线综述骨架"

# ③ 写完一个可评审单元 → 合并回 main（见 §6）
git switch main
git pull --ff-only
git merge --no-ff writing/ch02-lit-review
git push origin main

# ④ 分支用完即删
git branch -d writing/ch02-lit-review
```

### 2.3 什么时候该开新分支

- 要改**一章以上**的内容 → 开 `writing/<主题>`；
- 只改错别字、订正一处引用 → 直接在 main 上小提交也可（Lead 允许时）；
- 想尝试**推翻重写**某章 → 必须开分支，不要在 main 上"先删再写"。

## 3. 提交粒度

### 3.1 判断标准

一个提交应该满足：**回滚它不会破坏其他工作；看懂它不需要打开 diff。**

| 场景 | 合适粒度 |
| --- | --- |
| 补完一节正文 | 1 个提交 |
| 全章术语统一替换 | 1 个提交（`refactor`） |
| 更新 3 张图 + 图注 | 1–2 个提交（图件与图注分开也可） |
| 新增 5 条参考文献 + 正文引用 | 1 个提交（`docs(bib)`） |
| 改数据 + 改结果数值 + 改图 | **拆成 3 个提交**，否则无法单独回滚 |
| 排版调整 + 内容改写 | **必须拆**，否则评审分不清实质变化 |

### 3.2 反面例子

```
git add -A
git commit -m "update"
```

问题：无法回滚、无法评审、无法判断"update"改了什么。**禁止使用 `git add -A` 提交混装内容**；
至少用 `git add <具体路径>` 逐项暂存，并用 `git diff --staged` 检查后再提交。

## 4. Conventional Commits 中文规范

### 4.1 格式

```
<类型>(<范围>): <中文简述>

<可选正文：为什么改、改了什么、影响哪些章节>

<可选脚注：关联任务/评审意见/破坏性变更>
```

- **类型**用下表固定值（英文小写）；
- **范围**用中文或项目内既有代号（章号、目录名、模块名），保持全仓库一致；
- **简述**用中文，动词开头，不超过 30 字，句末不加句号；
- 正文与脚注用中文，可写多段。

### 4.2 类型表

| 类型 | 用于什么 | 例子 |
| --- | --- | --- |
| `feat` | 新增可用的内容/功能（新章节、新分析脚本、新图件） | `feat(ch06): 增加外部模型复现结果小节` |
| `fix` | 修正错误（数值、事实、引用、断链、语法错） | `fix(ch06): 修正表 6-3 出口时间均值` |
| `docs` | 文档与稿件文字修改（不含新增章节） | `docs(ch02): 重写 2.4 节缺口论证` |
| `refactor` | 不改变含义的重构（术语统一、结构调整、文件拆分） | `refactor: 全文统一"存量—流量"写法` |
| `test` | 测试相关（新增/修改测试、测试数据） | `test(core): 为硬阻挡补一条边界用例` |
| `chore` | 杂务（配置、脚本、忽略规则、依赖） | `chore: 添加 build/ 到忽略规则` |
| `build` | 导出/构建流程（pandoc 命令、模板、CI） | `build: 增加 docx 导出脚本` |
| `revert` | 回滚某次提交 | `revert: 回滚 3f2a1c9 的数值改动` |

### 4.3 范围（scope）词表

| 范围写法 | 指代 |
| --- | --- |
| `ch00` … `ch08` | 对应章节目录文件 |
| `paper` | `paper/` 整体（导航、导出约定） |
| `bib` | `paper/references.bib` 与引用 |
| `figures` / `tables` | 图件与表格 |
| `writing-doc` | `docs/writing/` 下的规范文件 |
| `workflow` | 分支/提交/评审流程本身 |
| `core` / `actors` | 源码模块（若修改代码） |

### 4.4 好例子 / 坏例子

| 场景 | 坏提交信息 | 好提交信息 |
| --- | --- | --- |
| 补写引言 | `update intro` | `feat(ch01): 补写 1.2 节三条脉络` |
| 改一个数字 | `fix` | `fix(ch06): 按 loop_demo_summary.json 更正喷泉变化率 82.7%→82.8%` |
| 批量改术语 | `修改` | `refactor: 全文"人在回路"统一为"人在回路（HITL）"` |
| 新增文献 | `add refs` | `docs(bib): 新增 3 条 C 线文献并接入 2.6 节` |
| 删掉一段 | `删除` | `docs(ch07): 删除无文献支撑的"规划实践现状"断言` |

### 4.5 正文与脚注

```
docs(ch06): 统一表 6-3 的数值精度

表 6-3 原为混合精度（192.0 / 121.83），与表注"统一 1 位小数"冲突。
现全部改为 1 位小数，并同步 §6.6 正文引用。

Refs: 评审意见 R-06-03
```

破坏性变更（例如重命名 bib key、改章节文件命名）必须在正文中写明：

```
refactor(bib): 重命名 3 条主键使其符合"姓年份_短标题"规则

BREAKING CHANGE: 正文中 [@Baez2022] 改为 [@Baez2022_StockFlowDiagrams]，
共影响 4 个章节文件。
```

## 5. 提交前自检清单

逐项打勾后再 `git commit`：

**格式层**

- [ ] 文件为 UTF-8 无 BOM、LF 换行、文件末尾一个空行；
- [ ] 章节文件保留 `## 本章目标 / ## 已有素材与证据锚点 / ## 待写作要点 / ## 状态` 四节；
- [ ] 正文区仍在 `<!-- BODY-START -->` 与 `<!-- BODY-END -->` 之间。

**事实层**

- [ ] 新增/修改的每个数字都能指到 `paper/README.md` §8 的素材文件；
- [ ] 没有把"模拟被试"写成"真人"、把"占位脚本"写成"LLM"；
- [ ] 未开展的工作（真人实验、在线实验、显著性）没有被写成结果。

**引用层**

- [ ] 每个 `[@key]` 都能在 `paper/references.bib` 解析；
- [ ] 新增文献条目有索引来源（`docs/papers*/index.json` 的 id），没有凭记忆补 DOI；
- [ ] 带 `% TODO: 待核实` 的条目没有被当作定稿文献。

**术语层**

- [ ] 术语与 [`术语表.md`](术语表.md) 一致（尤其"存量—流量""人在回路""合成智能体"）；
- [ ] 标点与数字格式符合 [`风格指南.md`](风格指南.md)。

**构建层**

- [ ] 本地能导出（至少跑通 `paper/manuscript.md` §4 的 docx 命令）；
- [ ] `pandoc --citeproc` 无未解析引用警告。

**范围层**

- [ ] `git status` 中没有误加入的临时文件（`build/`、`~$*.docx`、PDF 导出物）；
- [ ] 没有修改本次任务范围外的文件。

## 6. 写作评审循环

```
① 草案（写作分支）
      ↓  作者自查（§5 清单）
② 自查通过 → 发起交叉评审（review 分支快照）
      ↓  评审人按 §6.2 清单提意见（不改作者分支）
③ 作者逐条处理 → 每条一个提交（引用评审意见编号）
      ↓  评审人复核
④ 合并进 main → 更新章节状态与看板 → 更新 tag
```

### 6.1 发起评审

```powershell
# ① 确认写作分支已提交干净
git switch writing/ch02-lit-review
git status

# ② 由 Lead 在 main 的当前状态上打评审快照
git switch main
git pull --ff-only
git switch -c review/20261120
git push -u origin review/20261120
```

评审期间：**作者只改 `writing/...` 分支，评审人只在 `review/...` 分支上读**。
不要在评审快照上直接改内容，否则评审意见与版本对不上。

### 6.2 评审清单（评审人用）

- [ ] 缺口论证是否每一步都有文献或数据支撑；
- [ ] 声称的贡献是否超出证据（对照 06 章证据地图）；
- [ ] 数字是否与源文件一致（抽查 ≥3 处）；
- [ ] 术语、标点、图表编号是否一致；
- [ ] 引用是否可解析，是否存在未核实文献；
- [ ] 是否出现旧题名、旧平台名等过期表述；
- [ ] 是否可导出（不要求排版完美，要求可构建）。

### 6.3 把评审意见落成提交

约定评审意见编号：`R-<章号>-<序号>`（如 `R-06-03`）。处理时：

```powershell
git switch writing/ch02-lit-review
# 修改文件后
git add paper/sections/02-文献综述与研究缺口.md
git commit -m "docs(ch02): 按评审意见 R-02-05 删除无出处断言"
```

评审结束后由 Lead 合并：

```powershell
git switch main
git merge --no-ff writing/ch02-lit-review
git tag -a draft-20261120 -m "评审后合并快照：ch02 综述定稿"
git push origin main --tags
```

### 6.4 状态迁移必须与提交同步

章节状态（待写/初稿/修订中/定稿）的每次迁移，都要：

1. 改章节文件的 `## 状态`；
2. 改 `paper/manuscript.md` 看板与状态表；
3. 提交信息写清迁移：`docs(paper): ch02 综述 初稿→修订中`。

## 7. 冲突处理

### 7.1 为什么论文仓库也会冲突

- 两人同时改同一段论证；
- 一人批量替换术语，另一人同时修改该术语所在句子；
- 两人各自新增参考文献，`references.bib` 尾部冲突。

### 7.2 处理流程

```powershell
# ① 合并前先同步 main，把冲突解决在自己的分支上
git switch writing/ch02-lit-review
git fetch origin
git merge origin/main
# ② 出现冲突后，先看哪些文件
git status --short
```

冲突文件中的标记：

```
<<<<<<< HEAD
本文提出……
=======
本文构建……
>>>>>>> origin/main
```

处理原则：

1. **先理解两边为什么改**，不要无脑选一边；
2. 论文正文冲突的裁决优先级：**事实正确 > 术语一致 > 行文风格**；
3. 解决后删除所有 `<<<<<<<`、`=======`、`>>>>>>>` 标记（残留标记会让导出出现乱码）；
4. 用 `git diff --check` 确认没有残留冲突标记或行尾空白；
5. 解决后**必须重新跑一次导出**，再提交。

```powershell
git add paper/sections/02-文献综述与研究缺口.md
git commit -m "fix(ch02): 解决与 main 的合并冲突（保留事实更正版本）"
```

### 7.3 常见冲突的约定解法

| 冲突类型 | 约定解法 |
| --- | --- |
| 同一句被两人改写 | 保留事实更准确的一版，另一版可取表达合并；在提交正文说明取舍理由 |
| 术语批量替换 vs 句子改写 | 先合入句子改写，再重跑一次批量替换（`refactor` 单独提交） |
| `references.bib` 尾部新增冲突 | 两边条目都保留，按字母序重排；同一文献两库重复时只留一条（取已核验版本） |
| 图表编号冲突 | 按章号顺延，后合并者改号，并在表注/图注中说明 |

### 7.4 如果彻底搞砸了

```powershell
# 放弃本次合并，回到合并前
git merge --abort

# 丢弃某文件的未提交修改
git restore paper/sections/02-文献综述与研究缺口.md

# 查看最近的操作（找回误删分支/提交）
git reflog
```

## 8. 图表与数据快照如何随稿件打标签

### 8.1 原则：四者同 tag

**代码版本 + 数据快照 + 图件 + 正文**必须在同一个标签上，否则"这个数字是哪来的"
永远说不清。

### 8.2 打 tag 的两种时机

| 标签 | 何时打 | 用途 |
| --- | --- | --- |
| `draft-YYYYMMDD` | 每次评审快照 / 阶段性冻结 | 写作过程快照，可随时打 |
| `vX.Y.Z` | 里程碑（投稿、返修、定稿） | 对外版本，语义化版本号 |

```powershell
# 轻量快照：写作过程
git tag draft-20261120

# 附注标签：里程碑（推荐，带说明）
git tag -a v0.2.0 -m "论文 v0.2.0：ch02 定稿，ch06 数据口径统一"

# 推送标签
git push origin v0.2.0
```

### 8.3 数据快照的提交顺序

```powershell
# ① 先提交数据与代码（让数字可复现）
git add data/demo/loop_demo_summary.json examples/run_loop.py
git commit -m "feat(core): 更新闭环演示输出（200 轮×3 条件）"

# ② 再提交图件（图由数据生成）
git add results/repro/*.png
git commit -m "feat(figures): 重新生成图 6-1 至 6-4"

# ③ 最后提交正文数值与图注
git add paper/sections/06-结果与验证.md
git commit -m "docs(ch06): 同步表 6-1/6-2 与图 6-1 数值"

# ④ 四者同 tag
git tag -a v0.2.0 -m "ch06 结果口径统一（数据-图-文同版本）"
```

### 8.4 大文件与二进制

- 图件（PNG/SVG）可以入库，但**同一图不要反复提交大版本**；能重跑生成的图，
  优先只提交生成脚本与数据快照；
- 导出物（`build/*.docx`、`*.pdf`）**不入库**，通过 `.gitignore` 排除；
- 单文件超过 10 MB 时先问 Lead，再决定是否入库或改用外部存储 + 校验和。

## 9. AI 辅助写作的声明边界与致谢写法

### 9.1 必须声明的使用

- 使用大语言模型**生成或改写正文段落**（哪怕最终大改）；
- 使用模型**生成代码、脚本、数据转换逻辑**；
- 使用模型**辅助文献检索/摘要**，且其输出影响了论证或引用选择；
- 使用模型**翻译**（中→英摘要等）；
- 使用模型**起草图表说明、评审回复**等正式文本。

### 9.2 不必声明的情形

- 拼写与语法检查工具（含带 AI 的输入法、Word 语法检查）；
- 格式转换、参考文献格式化、导出脚本；
- 仅用于个人理解的检索，不影响稿件内容。

### 9.3 三条不可越过的边界

1. **事实与引用不得由模型编造**：所有文献条目、DOI、数据数值必须以仓库中的
   索引/PDF/数据文件为准；模型给出的"看起来合理"的引用一律视为未核实。
2. **核心学术判断由人负责**：研究问题、贡献主张、结论边界、评审回复的实质立场，
   必须由作者本人确认；不得以"模型这么说"作为论证依据。
3. **作者资格**：AI 工具**不得列为作者**，也不得作为通讯作者；作者须对全文负责。

### 9.4 声明模板（中文，置于致谢或方法节末）

```
本研究在写作过程中使用了大语言模型辅助 [具体用途：如英文摘要润色、文献摘要初筛、
代码调试]，所有由模型生成的文本均经作者逐句核验与改写，文中事实、数据与引用
由作者依据仓库内可核验材料确认，模型未参与研究设计、结果解释与结论形成。
模型使用情况：[工具名称与版本、使用日期区间]。
```

### 9.5 声明模板（英文，用于英文摘要或投稿系统）

```
During the preparation of this work the authors used [tool name/version] for
[language editing / literature screening / code debugging]. After using this tool,
the authors reviewed and edited the content as needed and take full responsibility
for the content of the publication. The tool was not used to generate research
findings, data, or citations.
```

### 9.6 致谢里还应该写什么

- 数据与代码来源（第三方模型、公开数据集及其许可）；
- 被试与实验协助（真人实验开展后）；
- 经费与项目支持（按资助方要求写编号）；
- **不写**：未实际参与的人、未获得的资助、无法核实的帮助。

## 10. 常见坑

| 坑 | 症状 | 处理 |
| --- | --- | --- |
| CRLF 混入 | diff 显示整文件被改；导出多空行 | `git config core.autocrlf input`，重存为 LF |
| BOM 混入 | 首行多出 ``；部分工具解析失败 | 用无 BOM 方式保存；`Get-Content -Encoding utf8` 检查 |
| 中文文件名 | 显示为 `\344\275\240` | `git config core.quotepath false` |
| 旧题名残留 | 评审指出题目不一致 | 合并前全文搜索旧题名关键词（见 `paper/manuscript.md` §5） |
| 临时文件入库 | 仓库出现 `~$xxx.docx`、`build/` | 检查 `.gitignore`，`git restore --staged` 撤出 |
| 在 main 上直接改 | 冲突与历史混乱 | 改用 `writing/` 分支 |
| 忘记拉取 | 推送被拒（non-fast-forward） | `git pull --ff-only` 后重试；冲突按 §7 处理 |

## 11. 速查卡

```powershell
# 看状态与差异
git status
git diff
git diff --staged
git log --oneline -15

# 开分支 / 切分支
git switch -c writing/ch03-model
git switch main

# 暂存与提交
git add paper/sections/03-研究框架与模型.md
git commit -m "docs(ch03): 补写 3.3 节守恒更新"

# 同步与合并
git fetch origin
git merge origin/main
git merge --no-ff writing/ch03-model

# 标签
git tag draft-20261120
git tag -a v0.2.0 -m "论文 v0.2.0"

# 找回
git reflog
git restore <文件>

# 只读检查（不修改任何内容）
git status --short
git diff --check
```

> **最后一条原则**：git 是写作的**证据链**，不是负担。当审稿人问"这个数字与
> 上一版为什么不同"时，你需要的不是记忆，而是一条能点开的提交记录。
