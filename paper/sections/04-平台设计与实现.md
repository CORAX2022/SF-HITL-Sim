## 4.1 设计第一原则：单一世界，同构接口

平台最关键的设计决策是：**真实人类被试与合成智能体，必须通过完全相同的接口与
同一个仿真世界交互。** 这条原则直接决定研究结论是否可信：

- 若人类走一套接口、合成体走另一套，二者的行为差异就**无法归因于"人 vs 机器"**，
  因为接口差异本身成了混淆变量；
- 若人类和合成体各跑一个世界实例，就**不能声称"共同驻留同一仿真环境"**，
  而这恰是本研究要挑战的缺口 G3；
- 只有单一世界 + 同构接口，才能做**受控替换实验**：固定场景与人设分布，把混合
  比例从 100% 真人逐步替换为 100% 合成体，观察宏观流量演化的偏移量。

据此，系统被切分为若干层，层间单向依赖；决策者的异质性被收敛到一个协议里。

## 4.2 分层架构

平台分为四层，另有一个可选外部服务：

- **实验交互层**：被试端（空间选择界面、状态可视化、主观感知量表、决策理由输入）
  与主试端（场景配置与启动、实时监控、混合比例控制、数据导出）；
- **仿真编排层**：轮次调度器、决策收集器、流量聚合器、约束/守恒投影器、
  空间图模型、背景流生成、数据记录器、状态广播器；
- **决策者层**：人类被试、合成智能体、规则背景体——三者实现同一协议；
- **持久层**：场景定义（JSON）、轮次日志（JSONL，事后转 SQLite/Parquet）、
  量表响应（CSV）、回放快照（JSONL）；
- **可选 LLM 服务**：人设与记忆管理、提示构造与解析、可插拔后端。

## 4.3 统一决策协议

人类与合成智能体都必须产出同一种结构化消息：

```jsonc
{
  "actor_id": "p03",              // 参与者匿名 ID 或合成体 ID
  "actor_type": "human",          // "human" | "llm" | "scripted"
  "round": 7,                     // 轮次
  "origin_unit": "plaza_north",   // 决策时所处单元
  "choice": "plaza_south",        // 目标单元 | "STAY" | "EXIT"
  "weight": 1.0,                  // 代表性权重
  "latency_ms": 4210,             // 决策耗时
  "confidence": 4,                // 自评把握 (1-5)，可选
  "reason": "南侧看起来人少",       // 开放文本，可选
  "issued_at": "2026-10-14T09:03:00+08:00"
}
```

设计要点有四：其一，`actor_type` **只用于标注与分组分析，仿真内核不得据此改变
计算逻辑**——内核看到的只是"一个权重为 `w` 的决策者从 `origin_unit` 选择了
`choice`"；其二，`weight` 使小样本外推成为可能（20 名真人可通过权重代表更大群体，
与合成体规模对齐）；其三，人类决策是异步到达的，收集器设决策窗口，超时未提交者按
`STAY` 处理并记录 `timed_out`，这本身就是有意义的被试行为数据；其四，合成体的
`latency_ms` 是真实推理耗时，可用于成本核算与分析，但不参与仿真状态演化。

该协议是"同构接口"原则的落地形式。任何新决策者（真人、LLM、规则体、未来接入的
强化学习体）只要实现该协议即可入网。

## 4.4 轮次生命周期

一轮的完整时序对应第 3 章 §3.6 的闭环：

1. 广播：向全体在网决策者下发状态快照；
2. 采集：开启决策窗口，人类前端提交、合成体本地推理、规则体立即产出，均写入缓冲；
3. 汇总：窗口关闭，汇总缓冲，标记超时者；
4. 聚合：背景重力流 + 人类流 + 合成体流 → 总流量；
5. 投影：守恒投影 + 容量惩罚/硬阻挡；
6. 推进：按守恒律更新状态；
7. 记录：落盘本轮决策、状态与量表；
8. 终止判定：轮次上限、参与者退出或主试终止。

**同步点**：只有在第 5–6 步之间存在全局同步；决策阶段是异步并行的，这样合成体
推理延迟不会阻塞人类被试的节奏，反之亦然。

## 4.5 内核实现

内核由三个组件构成，共约六百行 Python（含注释），不依赖任何编译扩展：

**空间图 `SpaceGraph`**。以单元列表与有向边列表构造，内部维护邻接矩阵、通行成本矩阵
及各单元的容量、硬容量、移动倾向、吸引力、出口率向量，并提供邻接查询、邻居列表、
可达性（BFS）、场景结构校验（重复 id、未知单元、不可达单元等）与 JSON 读写。
演示场景为 12 个单元、46 条有向边。

**流量模型 `FlowModel`**。无状态（除参数外），因此便于单元测试与批量情景扫描。
其 `gravity_flows` 实现 §3.4 的重力流，`decision_flows` 把决策列表聚合为流量矩阵并
校验可达性（非法选择直接抛错），`effective_cost` 实现拥挤惩罚与硬阻挡，
`project_conservation` 实现比例投影，`compose` 把背景流、决策流、边界流与全部约束
合成为一次完整流量。

**仿真内核 `SimulationKernel`**。持有唯一世界状态，提供 `state_snapshot()`（只暴露
聚合量，不泄露个人身份信息）、`step()`（推进一轮并返回 `RoundRecord`）、
`run()`（多轮）与 `check_conservation()`（单轮守恒自检）。`RoundRecord` 记录推进前后
状态、流量摘要、利用率、决策与硬阻挡事件，**足以完整回放**。内核在推进时对浮点
微小负值做数值清理，并在偏差超过阈值时抛出 `ConservationError`，属于"必须立即暴露
的严重错误"。

## 4.7 技术选型与工程风险

选型原则是"科学计算同栈 + 实验期抗崩溃"：内核用 Python（科学计算生态、易与分析
同栈）；人类实验前端候选 jsPsych（精确计时、成熟行为实验范式）与 oTree 式房间
（多人同步轮次 + 问卷）；通信采用 WebSocket 实时推送 + REST 配置/导出；数据以
JSONL + CSV 实验期落盘、事后转 SQLite/Parquet；LLM 采用可插拔后端以兼顾成本与
数据合规。需要强调的是：SUMO、CityFlow、AB Street 等精细仿真引擎**不是**本平台的
运行内核，它们仅提供场景数据格式、标定参考与多尺度接驳时的局部精化能力，
并作为聚合近似误差的对照组。

主要工程风险与对策：决策窗口与真实网络延迟（服务端统一计时、`window_ms` 可配置、
记录真实 `latency_ms`）；多人会话状态丢失（每轮落盘、快照恢复、断线重连）；
LLM 延迟与成本波动（决策阶段异步、超时按 STAY 记录）；LLM 输出格式不合规
（强制结构化输出 + 重试 + 失败降级为 STAY 并标记）；守恒约束被违反导致发散
（强制比例投影，**不可跳过**）；被试样本量小（权重机制，同时报告未加权与加权结果）；
真人数据合规（匿名化 ID、知情同意、仅存聚合量、伦理审查前置）；上游许可证冲突
（逐仓库核对 SPDX，避免 AGPL 污染）。

## 4.8 环境限制

本机开发环境无 C/C++ 编译器、无 CMake、无 Julia、无 conda，因此需要编译的上游
引擎（SUMO 源码、CityFlow、AB Street）无法在本机构建，只能做静态分析与库层面验证；
各验证报告已如实记录这一点，并给出在有编译环境的机器上完成构建的确切命令。
平台内核因此为纯 Python 实现，不引入编译依赖——这既是限制，也降低了复现门槛。
